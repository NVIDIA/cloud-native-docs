DCGM Exporter with the NVIDIA GPU Operator#

DCGM Exporter reads GPU metrics from NVIDIA DCGM and exposes them for Prometheus at /metrics. The NVIDIA GPU Operator deploys DCGM Exporter on every GPU node by default.

This page covers what the GPU Operator does for DCGM Exporter and how you configure it through the Operator. For DCGM Exporter itself, refer to the DCGM Exporter documentation:

  • Install DCGM Exporter, including standalone containers, packages, and the exporter’s own Helm chart.

  • Command-line and YAML reference for options, environment variables, and the configuration file.

  • DCGM Exporter metrics for metric names, units, labels, and MIG behavior.

  • Configure Prometheus for DCGM Exporter.

  • DCGM Exporter release notes, including the metric name changes in DCGM Exporter 4.9.0.

What the Operator Deploys#

The Operator creates the following resources in the Operator namespace, such as gpu-operator:

Resource

Description

DaemonSet nvidia-dcgm-exporter

Runs one DCGM Exporter pod on each node that has the nvidia.com/gpu.deploy.dcgm-exporter=true label. The pods have the app=nvidia-dcgm-exporter label.

Service nvidia-dcgm-exporter

Exposes port 9400, named gpu-metrics.

ServiceMonitor nvidia-dcgm-exporter

Tells the Prometheus Operator to scrape /metrics on the gpu-metrics port. The GPU Operator creates it only when dcgmExporter.serviceMonitor.enabled is true and the ServiceMonitor custom resource definition exists in the cluster.

PrometheusRule nvidia-dcgm-exporter

OpenShift only. Records the accelerator_* series that the OpenShift console uses. Refer to Enabling the GPU Monitoring Dashboard.

By default, DCGM Exporter runs an embedded DCGM host engine inside its container.

The Operator sets the following environment variables on the exporter container:

  • DCGM_EXPORTER_LISTEN=:9400

  • DCGM_EXPORTER_KUBERNETES=true, which adds pod, namespace, and container labels to the metrics of GPUs that pods use.

  • DCGM_EXPORTER_COLLECTORS=/etc/dcgm-exporter/default-counters.csv, the default metrics file in the image. When you supply a custom metrics file, the value is /etc/dcgm-exporter/dcgm-metrics.csv.

  • DCGM_REMOTE_HOSTENGINE_INFO=nvidia-dcgm:5555, only when the standalone DCGM host engine is enabled. For a GPUCluster with standalone DCGM, the value is nvidia-dcgm-dra:5555.

Variables in dcgmExporter.env are applied last and replace these values. Environment variables also take precedence over the exporter’s configuration file, /etc/dcgm-exporter/config.yaml, in the image.

DCGM Exporter 4.9.0 stops at startup on more invalid settings. An invalid value in dcgmExporter.env or dcgmExporter.args stops the pod with an error message. To see the message, view the pod logs:

$ kubectl logs -n gpu-operator -l app=nvidia-dcgm-exporter

Custom Metrics Files#

By default, DCGM Exporter collects the metrics in /etc/dcgm-exporter/default-counters.csv in the image. To collect a different set, supply your own metrics file in a ConfigMap. For the file format and the available metrics, refer to DCGM Exporter metrics.

DCGM Exporter 4.9.0 uses the DCGM 4.7 field names, such as DCGM_FI_DEV_GPU_UTIL_RATIO. It still loads the older names, such as DCGM_FI_DEV_GPU_UTIL, but they are deprecated. A metric that uses an older name keeps that name and its older unit.

  1. Create a ConfigMap in the Operator namespace. Store the file under the key dcgm-metrics.csv:

    $ kubectl create configmap custom-dcgm-exporter-metrics -n gpu-operator \
    --from-file=dcgm-metrics.csv=./dcgm-metrics.csv

  2. Set dcgmExporter.config.name to the ConfigMap name. With Helm:

    $ helm upgrade gpu-operator nvidia/gpu-operator -n gpu-operator \
    --reuse-values --set dcgmExporter.config.name=custom-dcgm-exporter-metrics

    Or patch the cluster policy:

    $ kubectl patch clusterpolicies.nvidia.com/cluster-policy --type=merge \
    -p '{"spec": {"dcgmExporter": {"config": {"name": "custom-dcgm-exporter-metrics"}}}}'

The Operator mounts the file at /etc/dcgm-exporter/dcgm-metrics.csv and sets DCGM_EXPORTER_COLLECTORS to that path. The ConfigMap replaces only the metrics file. The configuration file in the image still applies.

Instead of the first step, you can have the Helm chart create the ConfigMap. Set dcgmExporter.config.create=true and put the file contents in dcgmExporter.config.data.

Note

The Operator mounts the file with subPath, so Kubernetes does not update the file in running pods when you edit the ConfigMap. After you change the ConfigMap, restart the DCGM Exporter pods:

$ kubectl delete pod -n gpu-operator -l app=nvidia-dcgm-exporter

Do not use the DCGM_EXPORTER_CONFIGMAP_DATA environment variable to read metrics from a ConfigMap. It is deprecated in DCGM Exporter 4.9.0 and logs a warning at each start.

Collecting Metrics in Prometheus#

If your cluster runs the Prometheus Operator, for example through the kube-prometheus-stack Helm chart, install it, or at least its custom resource definitions, before the GPU Operator. The GPU Operator then creates the nvidia-dcgm-exporter ServiceMonitor.

Prometheus must select the ServiceMonitor. By default, kube-prometheus-stack selects only ServiceMonitor objects that have its release label. Do one of the following:

  • Add the label through the GPU Operator:

    $ helm upgrade gpu-operator nvidia/gpu-operator -n gpu-operator \
    --reuse-values --set dcgmExporter.serviceMonitor.additionalLabels.release=<prometheus-release-name>

  • Configure Prometheus to select all ServiceMonitor objects. In kube-prometheus-stack, set prometheus.prometheusSpec.serviceMonitorSelectorNilUsesHelmValues=false.

To check that Prometheus collects the metrics, query a default metric, such as DCGM_FI_DEV_GPU_UTIL_RATIO. DCGM Exporter 4.9.0 and later use this name, and the value is a ratio from 0 to 1. Earlier versions use DCGM_FI_DEV_GPU_UTIL, in percent.

If you do not use the Prometheus Operator, scrape the nvidia-dcgm-exporter service on port 9400. Refer to Configure Prometheus for DCGM Exporter.

For a Grafana dashboard, import dcgm-exporter-dashboard.json from the DCGM Exporter repository. The dashboard on the main branch uses the metric names of DCGM Exporter 4.9.0 and later. For an earlier version, use the file from the matching release tag. On OpenShift, refer to Enabling the GPU Monitoring Dashboard.

Metrics for Shared GPUs and MIG#

With GPU time-slicing or MPS, set KUBERNETES_VIRTUAL_GPUS=true in dcgmExporter.env so that the metrics are associated with the pods that share the GPU. Refer to Time-Slicing GPUs in Kubernetes.

With MIG, DCGM Exporter reports metrics for each GPU instance. The MIG Manager stops the DCGM Exporter pods while it changes the MIG configuration of a node. For the MIG labels and metrics, refer to DCGM Exporter metrics.

Using a Separate DCGM Host Engine#

By default, each DCGM Exporter pod runs its own embedded DCGM host engine. You can use a separate host engine instead:

  • Standalone DCGM from the Operator. Set dcgm.enabled=true. The Operator deploys the nvidia-dcgm daemon set and points DCGM Exporter at the nvidia-dcgm service on port 5555. The default ClusterPolicy on OpenShift sets dcgm.enabled to true.

  • DCGM on the host, such as on NVIDIA DGX systems. Keep dcgm.enabled=false and point DCGM Exporter at the host engine on the node:

    dcgmExporter:
  hostNetwork: true
  env:
  - name: DCGM_REMOTE_HOSTENGINE_INFO
    value: localhost:5555

DCGM Exporter 4.9.0 needs a DCGM 4.7.0 host engine. With an older host engine, DCGM Exporter 4.9.0 exits at startup, because its default metrics use DCGM 4.7 fields. With a newer host engine, such as DCGM 4.7.1, NVSwitch discovery fails. Other pairings are untested and unsupported. Use the DCGM and DCGM Exporter versions that the Operator release ships. If you set dcgm.version, upgrade it together with dcgmExporter.version.

For more information, refer to Connect to a DCGM host engine.
